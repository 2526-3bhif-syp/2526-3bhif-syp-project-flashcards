== Architektur

=== Layer-Architektur (Frontend-fokussiert)

....
frontend/src/main/java/at/htlleonding/flashcards/
├── model/                # Fachliches Datenmodell & Logik
│   ├── Card.java         # Entity
│   ├── Deck.java         # Entity
│   ├── Session.java      # Lern-Sitzung Logik
│   └── Persistence.java  # JSON Storage Service
├── view/                 # JavaFX UI Komponenten (No FXML)
│   ├── MainView.java     # Root Layout
│   ├── SidebarView.java  # Navigation
│   └── *View.java        # Content-spezifische Views
├── presenter/            # Bindeglied (MVP)
│   ├── MainPresenter.java
│   └── *Presenter.java   # Spezifische Presenter für Views
└── Main.java             # JavaFX Application Entry
....

=== Schichten-Regeln

[IMPORTANT]
====
* `view/` -> Rein deklaratives Layout im Java-Code. Keine Geschäftslogik.
* `presenter/` -> Reagiert auf View-Events, manipuliert das `model` und aktualisiert die `view`.
* `model/` -> Enthält Datenstrukturen, den Lern-Algorithmus (BR-003) und die JSON-Serialisierung.
* `Persistence` -> Kapselt den Zugriff auf das Dateisystem (JSON/Base64).
====

== Coding-Konventionen

=== Allgemein
* Package-Prefix: `at.htlleonding.flashcards`
* Keine Wildcards in Imports
* Records für reine Datencontainer (wo sinnvoll)
* JavaFX-Properties für Data-Binding verwenden

=== Naming
* Klassen: PascalCase
* Methoden/Variablen: camelCase
* Konstanten: SCREAMING_SNAKE_CASE
* Views: `*View.java`
* Presenter: `*Presenter.java`
* Modelle: Substantive (z.B. `Card`, `Deck`)

== Mapping: FSD → Code

[cols="1,2,2"]
|===
| FSD-Element | Code-Artefakt | Beispiel

| Stapel (Deck)
| Klasse in `model/`
| `Deck.java`

| Karte (Card)
| Klasse in `model/`
| `Card.java`

| Selbsteinschätzung
| Enum in `model/`
| `Difficulty.java` (FALSCH, SCHWIERIG, OK, LEICHT)

| US-003: Lernsitzung
| Logik in `Session.java` & `FlashcardsPresenter.java`
| `Session.getNextCard()`

| BR-004: Datenformat
| Jackson Mixins/Service in `Persistence.java`
| `Persistence.export(Deck deck)`
|===

== Workflow für Agent (Claude Code)

=== Bei neuen Implementierungsschritten

1. `specs/fsd.adoc` für Anforderungen prüfen
2. `agents.adoc` für Architektur-Vorgaben prüfen
3. Model-Klassen erstellen/erweitern
4. Unit-Tests für Logik schreiben
5. Presenter-Logik implementieren
6. View-Elemente in JavaFX ergänzen (Code-only)
7. Manuelle Verifikation der UI

=== Regeln

* **Kein FXML:** UI wird ausschließlich in Java-Code gebaut.
* **Single Source of Truth:** Anforderungen kommen aus `fsd.adoc`.
* **State Management:** Navigation über `MainPresenter` (Stack-basiert wie bereits vorhanden).
* **Fehlerbehandlung:** Robuste Fehlerbehandlung beim Datei-I/O (JSON).
